## Overview

Add local closeout reminders for jobs that are accepted, scheduled, or completed but still need closeout details before they are payout-ready or operationally clear. The feature keeps reminders inside the app only. It does not send push notifications, customer messages, email, SMS, or RepairShopr writes.

The existing database already has a `reminders` table with `jobId`, `reason`, `resolvedAt`, and `createdAt`. This is enough for v1 because reminder identity can be represented by strict shared reason codes, and the API can sync unresolved rows by job and reason. No migration is planned.

## Reminder Rules

Generate reminders for jobs in `accepted`, `scheduled`, or `completed` state. Do not generate reminders for `payout_ready` or `closed` jobs.

Reason codes:

- `missing_completion`: job is accepted or scheduled and has no completion marker.
- `missing_split_category`: job has no split category.
- `missing_charge_or_profit`: job has neither reported profit nor gross charge.
- `missing_expense_detail`: job uses charge-based profit, has no reported profit, and has no expense rows.
- `missing_follow_up`: no follow-up status has been captured for the job.
- `follow_up_needed`: the latest follow-up fact says follow-up is needed.

The generation pass syncs the table to these derived reasons:

- Insert missing unresolved reminders for current reasons.
- Resolve unresolved reminders whose reason no longer applies.
- Preserve existing unresolved reminders whose reason still applies.

Manual resolve is still available for quick follow-up completion. If a manually resolved missing-field reminder still applies on the next generation pass, the service may recreate it because the missing field was not actually filled.

## API Shape

### `GET /reminders`

Requires `tech` or `manager` role.

Returns unresolved reminders sorted by newest first:

```json
{
  "reminders": [
    {
      "id": "00000000-0000-4000-8000-000000180001",
      "jobId": "00000000-0000-4000-8000-000000010102",
      "jobState": "scheduled",
      "customerLabel": "Scheduled onsite setup",
      "reason": "missing_completion",
      "createdAt": "2026-05-26T12:00:00.000Z",
      "resolvedAt": null,
      "stale": false
    }
  ]
}
```

### `POST /reminders/generate`

Requires `tech` or `manager` role.

Runs reminder generation immediately and returns:

```json
{
  "createdCount": 2,
  "resolvedCount": 1,
  "reminders": []
}
```

### `POST /reminders/:reminderId/resolve`

Requires `tech` or `manager` role.

Marks one unresolved reminder resolved and returns:

```json
{
  "reminder": {
    "id": "00000000-0000-4000-8000-000000180001",
    "jobId": "00000000-0000-4000-8000-000000010102",
    "jobState": "scheduled",
    "customerLabel": "Scheduled onsite setup",
    "reason": "follow_up_needed",
    "createdAt": "2026-05-26T12:00:00.000Z",
    "resolvedAt": "2026-05-26T13:00:00.000Z",
    "stale": false
  }
}
```

### `GET /manager/reminders/stale`

Requires `manager` role.

Returns unresolved reminders older than the stale threshold. The service uses 24 hours for v1.

### `apps/api/src/repositories/reminders-repository.ts`

Add:

- `ReminderCandidateRecord`
- `ReminderRecord`
- `ReminderSyncResult`
- `RemindersRepository`

Repository methods:

- `listCloseoutCandidates()`
- `syncRemindersForJob(jobId, reasons, now)`
- `listOpenReminders(now, staleAfterMs)`
- `listStaleReminders(now, staleAfterMs)`
- `resolveReminder(reminderId, now)`

Implementation details:

- Read candidate jobs in `accepted`, `scheduled`, and `completed` states.
- Count expense rows per candidate job.
- Read follow-up facts from `extracted_facts` and use the latest `follow_up_needed` fact per job.
- Sync unresolved reminders in a transaction per job.
- Do not add a migration because the current `reminders.reason` text column can hold strict application-level reason codes.

### `apps/api/src/services/reminder-service.ts`

Add:

- `ReminderStore`
- `ReminderServiceApi`
- `ReminderService`
- `ReminderNotFoundError`

Responsibilities:

- Derive closeout reasons from each candidate.
- Generate and sync reminders.
- List open reminders for tech and manager users.
- List manager stale reminders.
- Resolve one reminder.
- Parse repository rows through shared schemas before returning route responses.

### `apps/api/src/jobs/reminder-job.ts`

Add:

- `ReminderJobRunner`
- `DEFAULT_REMINDER_JOB_INTERVAL_MS`

The runner calls `ReminderServiceApi.generateReminders()` once on start and then at the interval. It logs failures through the Fastify logger but does not throw after startup. It stops its interval on app shutdown.

- `GET /reminders`

Route rules:

- `GET /reminders`, `POST /reminders/generate`, and resolve allow `tech` and `manager`.
