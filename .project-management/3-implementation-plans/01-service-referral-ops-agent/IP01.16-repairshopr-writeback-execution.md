# IP01.16 - RepairShopr Writeback Execution - Implementation Plan

**Date:** 2026-05-26
**Story Points:** 8
**Project Plan:** PP01-service-referral-ops-agent
**Local Ticket:** RSJT-016
**Dependencies:** RSJT-005, RSJT-008, RSJT-015

## Overview

Execute approved RepairShopr writebacks from the local approval queue while preserving the project's safety boundaries. The system should create a local execution record when an executable approval becomes approved, run only approved payloads, persist request and response details, surface failures for retry, and keep live external writes disabled unless explicitly enabled in local config.

Fresh documentation check:

- RepairShopr REST API docs were checked on 2026-05-26. RepairShopr documents Swagger-based REST APIs, API token setup, and a 180 requests per minute per IP rate limit. The docs warn that Swagger `Post` and `Put` requests can modify live site data, so this plan keeps tests fixture-backed and gates live writes.
- Twilio Message Resource docs were checked on 2026-05-26. Twilio creates outbound messages through `POST /2010-04-01/Accounts/{AccountSid}/Messages.json`, requires recipient, sender, and message content, and returns message status values such as `queued`, `sent`, `failed`, and `undelivered`. Customer-message execution stays behind the existing disabled-first Twilio messenger.
- Expo Router docs were checked on 2026-05-26. The writeback retry UI uses the existing file-based route pattern under the tech route group and typed routes will be regenerated after new route files are added.

## Proposed Structure

- Add shared writeback DTOs and payload schemas so approval payloads are no longer untyped at execution time.
- Add a `writeback_executions` table keyed to approved approvals.
- Extend the approval service with an optional execution handoff that creates or refreshes a ready execution record after approval.
- Add a sibling `RepairShoprWriteClient`; do not add write methods to the read-only RepairShopr client.
- Add `WritebackExecutionService` for approved-only execution, retry, and audit event persistence.
- Add API routes for listing executions, executing an approved approval, and retrying a failed execution.
- Add mobile tech writeback review screens for ready, failed, and succeeded executions.
- Keep `REPAIRSHOPR_WRITEBACK_ENABLED=false` and `MESSAGING_OUTBOUND_ENABLED=false` as safe defaults.

## Safety Rules

- No RepairShopr write method can run unless the linked approval is in `approved` state.
- No customer-facing message can be sent unless its linked approval is in `approved` state and `MESSAGING_OUTBOUND_ENABLED=true`.
- No RepairShopr write can be attempted unless `REPAIRSHOPR_WRITEBACK_ENABLED=true`.
- Tests must use fixture transports or fake executors only.
- The read-only `RepairShoprClient` remains read-only.
- Every execution attempt records an audit event with redacted request details, response details, or error details.
- Failed writebacks remain visible and retryable from local API and mobile UI.

## API Shape

### `GET /writebacks`

Requires `tech` or `manager` role.

Query filters:

- `state`: optional `ready`, `succeeded`, `failed`, or `blocked`.
- `approvalId`: optional UUID.
- `jobId`: optional UUID.

Returns:

```ts
{
  executions: WritebackExecution[];
}
```

### `POST /writebacks/approvals/:approvalId/execute`

Requires `tech` or `manager` role.

Behavior:

- Loads the approval.
- Requires `approval.state === "approved"`.
- Creates a ready execution row if the approval has no execution row yet.
- Executes the writeback when the matching external-write config gate is enabled.
- Returns blocked state when the config gate is disabled.

Returns:

```ts
{
  execution: WritebackExecution;
}
```

### `POST /writebacks/:executionId/retry`

Requires `tech` or `manager` role.

Behavior:

- Requires `execution.state === "failed"` or `execution.state === "blocked"`.
- Reuses the original approval payload.
- Attempts execution again if the config gate is enabled.

Returns:

```ts
{
  execution: WritebackExecution;
}
```
