# IP01.15 - Scheduling Proposal And Approval - Implementation Plan

**Date:** 2026-05-26
**Story Points:** 5
**Project Plan:** PP01-service-referral-ops-agent

**Dependencies:** RSJT-008, RSJT-013, RSJT-014

## Overview

Add scheduling preference extraction, proposal staging, and tech approval UI. The system should collect scheduling preferences from customer and tech messages, stage customer-facing scheduling wording and RepairShopr appointment proposal payloads, and require explicit tech approval before any scheduling commitment becomes eligible for outbound messaging or RepairShopr writeback.

This ticket does not send customer messages and does not create RepairShopr appointments. It only stages proposals and approval decisions in the local app.

Fresh documentation check:

- Twilio outbound docs were checked on 2026-05-26. Customer-facing sends remain behind the outbound service from IP01.14 and disabled by default.
- Expo Router notation confirms the planned tech scheduling route maps cleanly under `/tech/scheduling`.
- TanStack Query mutation guidance matches the existing pattern for approve/edit/reject actions.

## Proposed Structure

- Add shared scheduling proposal DTOs.
- Add a `schedulingProposals` table linked to conversations, optional jobs, and approvals.
- Add a deterministic scheduling proposal service that reads scheduling facts from intake and tech messages.
- Use the existing approvals engine for tech approval of:
  - customer-facing scheduling message wording.
  - RepairShopr appointment proposal payload.
- Add tech API routes for listing, editing, approving, and rejecting scheduling proposals.
- Add tech mobile UI for reviewing proposed time windows and message wording.
- Keep all outbound sends and RepairShopr appointment writes out of scope.

## Safety Rules

- A customer-facing message must not include confirmed time, arrival window, or availability unless its proposal has an approved tech decision.
- A RepairShopr appointment payload must not be marked eligible for writeback unless its proposal has an approved tech decision.
- Proposed wording can mention that the tech will confirm availability, but unapproved wording must not be sent.
- Approved proposal state means locally approved only. It does not send a message or create an appointment in this ticket.

## API Shape

### `GET /tech/scheduling/proposals`

Requires `tech` or `manager` role.

Returns pending and recently decided scheduling proposals.

### `GET /tech/scheduling/proposals/:proposalId`

Requires `tech` or `manager` role.

Returns a proposal with source evidence and linked approval records.

### `PATCH /tech/scheduling/proposals/:proposalId`

Requires `tech` or `manager` role.

Updates proposed customer wording and preferred window before approval.

### `POST /tech/scheduling/proposals/:proposalId/approve`

Requires `tech` or `manager` role.

Approves the proposal locally and approves linked pending approvals.

### `POST /tech/scheduling/proposals/:proposalId/reject`

Requires `tech` or `manager` role.

Rejects the proposal locally and rejects linked pending approvals.

Methods:

- `generateFromConversation(conversationId)`
- `listProposals(user)`
- `getProposal(user, proposalId)`
- `editProposal(user, proposalId, input)`
- `approveProposal(user, proposalId)`
- `rejectProposal(user, proposalId, reason)`

Generation rules:

- Use scheduling notes from extracted facts when linked to a job.
- Use intake preferred timing when linked to a conversation.
- Create a customer-message approval with `kind = "customer_message"`, `risk = "scheduling"`, and `requiredRole = "tech"`.
- Create an appointment approval with `kind = "appointment_creation"`, `risk = "scheduling"`, and `requiredRole = "tech"` when enough date/time context exists.
- Do not create RepairShopr appointments.
- Do not send customer messages.

Validation rules:

- Reject customer wording that contains direct confirmations such as `confirmed`, `booked`, `we will be there`, or a precise arrival window unless the proposal is being approved in the same action.
- Even after approval, do not send the wording. Approval only marks it eligible for later explicit send.
- Require source evidence for every generated proposal.
