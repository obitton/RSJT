# IP01.7 - Tech Update Extraction Service - Implementation Plan

**Date:** 2026-05-22
**Story Points:** 8
**Project Plan:** PP01-service-referral-ops-agent
**Local Ticket:** RSJT-007
**Dependencies:** RSJT-002, RSJT-003, RSJT-004

## Overview

Build the backend service that turns terse tech job updates into structured facts with confidence, missing-field prompts, and source evidence. This creates the first usable ingestion path for technician job updates without making live AI calls in tests and without introducing person names into code, database values, fixtures, or route names.

The implementation should be provider-ready, not provider-faked. V1 adds an extraction adapter interface and a deterministic local adapter for tests and local development. A live AI provider can be added behind the same interface once credentials and provider choice are configured.

## Proposed Structure

- Add shared extraction contracts under `packages/shared/src/domain/extraction.ts`.
- Store extracted facts through a focused repository that validates fact type, confidence, and evidence before insert.
- Add a message repository so update extraction always has a real `messages.id` as source evidence.
- Add `UpdateExtractionService` with adapter, missing-field, and persistence responsibilities.
- Add an initial deterministic adapter that handles known local patterns and is clearly named as deterministic.
- Add authenticated update routes under `/jobs/:jobId/updates/extract`.
- Keep route behavior generic: authenticated `manager` and `tech` users can submit internal updates in V1.

## File-By-File Changes

### `packages/shared/src/domain/extraction.ts`

Create shared schemas and types for extraction:

- `ExtractedFactValueSchema` as a discriminated union keyed by current `ExtractedFactTypeSchema` values.
- `ExtractedFactSchema` with `type`, `value`, `confidence`, `evidence`, and `requiresConfirmation`.
- `MissingFieldSchema` limited to fields the app can ask about in V1.
- `MissingFieldPromptSchema` with `field` and `message`.
- `UpdateExtractionRequestSchema` with a trimmed non-empty `body`.
- `UpdateExtractionResponseSchema` with `jobId`, `messageId`, `facts`, `missingFields`, and `prompts`.

The value schema should cover:

- `customer_hint`: `{ text: string }`
- `work_performed`: `{ text: string }`
- `duration_minutes`: `{ minutes: number }`
- `gross_charge_cents`: `{ amountCents: number }`
- `expense_cents`: `{ amountCents: number, description?: string }`
- `reported_profit_cents`: `{ amountCents: number }`
- `completion_state`: `{ state: "completed" | "not_completed" | "likely_completed" | "unknown" }`
- `scheduling_note`: `{ text: string }`
- `follow_up_needed`: `{ needed: boolean, note?: string }`

### `packages/shared/src/index.ts`

Export the new extraction domain module.

### `packages/shared/src/domain/domain.test.ts`

Add focused schema tests:

- Valid update extraction request accepts non-empty body.
- Empty body is rejected.
- Money, duration, and evidence facts parse.
- Invalid fact value/type combinations are rejected.

### `apps/api/src/repositories/messages-repository.ts`

Add a small repository with:

- `createJobUpdateMessage(input)` to insert a message linked to a job.
- Direction set to `internal`.
- `authorRole` populated from the authenticated session role.
- No customer-facing send behavior.

### `apps/api/src/repositories/extracted-facts-repository.ts`

Add a repository with:

- `replaceForMessage(jobId, messageId, facts)` to delete existing facts for the message and insert current extraction output.
- `listForMessage(messageId)` for tests and future API use.
- `confidence` stored as basis points.
- `value` and `evidence` stored as JSON after shared schema validation.

The repository should not update job totals yet. Downstream writeback and money reconciliation remain staged by later tickets.

### `apps/api/src/services/update-extraction-service.ts`

Add:

- `UpdateExtractionAdapter` interface.
- `DeterministicUpdateExtractionAdapter` for local/test extraction.
- `UpdateExtractionService` orchestration.
- Missing-field prompt generation.
- Confirmation rules.

Confirmation rules:

- Any fact below `0.8` confidence requires confirmation.
- All `customer_hint`, `gross_charge_cents`, `expense_cents`, `reported_profit_cents`, `completion_state`, `scheduling_note`, and `follow_up_needed` facts require source evidence.
- Missing `expense_cents` should produce a prompt unless the update explicitly says no expenses, no parts, or no materials.
- Missing `completion_state` should produce a prompt when no completion signal is present.
- Missing `customer_hint` should produce a prompt when no likely customer, phone, email, ticket, or name appears.

Deterministic adapter behavior:

- Parse durations such as `1 hr`, `1 hour`, `90 min`, and `2 hours`.
- Parse simple charge phrases such as `$200`, `charged 200`, and trailing standalone amounts after a duration.
- Parse expenses from phrases like `parts 40`, `materials $40`, and `expense 40`.
- Parse no-expense phrases like `no parts`, `no materials`, and `no expenses`.
- Infer `likely_completed` from short visit summaries with a duration and charge.
- Keep every extracted fact tied to the exact quote when possible.

### `apps/api/src/routes/updates-routes.ts`

Add authenticated route registration:

- `POST /jobs/:jobId/updates/extract`
- Validate route params with `JobIdParamsSchema`.
- Validate payload with `UpdateExtractionRequestSchema`.
- Require an authenticated user.
- Create an internal message, extract facts, persist facts, and return typed response.
- Return `503` if the extraction service is unavailable.

### `apps/api/src/app.ts`

Wire the route and default service:

- Add optional `updateExtractionService` to `AppOptions`.
- Register update routes after auth routes.
- Create default service only when `db` is decorated.
- Do not require live AI configuration for app startup.

### Tests

Add tests for:

- Service extraction of `"went to Michele, 1 hr 200"`.
- Evidence and confirmation behavior for money, completion, and identity facts.
- Missing-field prompts.
- Repository persistence with JSON fact values and evidence.
- Route authentication, validation, happy path, and unavailable service response.

## Implementation Boundaries

- Do not call live AI providers in this ticket.
- Do not send SMS, WhatsApp, email, or other external messages.
- Do not write to RepairShopr.
- Do not update job money fields automatically from extracted facts.
- Do not introduce person names into code, fixtures, route names, DB enums, or env vars.
- Do not touch Linear, Notion, Slack, Gmail, Google Drive, or Tenex-owned systems.
