# IP01.13 - Customer Intake State Machine And Spam Gate - Implementation Plan

**Date:** 2026-05-26

## Overview

Build the conservative customer intake state machine on top of persisted messaging webhooks. The system should track whether an inbound customer conversation is unknown, identifying, collecting details, matched, review-ready, or blocked. It should collect only missing fields, apply deterministic spam controls, use RepairShopr matching when available, and stage local approvals for customer/lead writebacks only after minimum data and spam checks pass.

This ticket does not send customer-facing replies. It can generate the next suggested intake prompt and stage it as a local approval, but actual outbound messaging remains blocked until the later outbound ticket and explicit credentials.

Fresh documentation check:

- Twilio webhook docs were checked on 2026-05-26. Inbound messages arrive through the webhook route built in IP01.12.
- Twilio warns that webhook parameters may evolve, so the state machine should read the normalized message record rather than depending on every raw Twilio field.
- Existing project matching rules use RepairShopr reads only and already support high, medium-high, and low confidence bands.

Sources:

- https://www.twilio.com/docs/usage/webhooks/messaging-webhooks
- https://www.twilio.com/docs/messaging/guides/webhook-request

## Proposed Structure

- Add shared intake state, field, prompt, and evaluation DTOs.
- Add intake fields to the `conversations` table so each customer thread has one current state snapshot.
- Add an `IntakeStateMachineService` that evaluates a conversation after each inbound message.
- Add deterministic spam checks before staging any customer or lead writeback.
- Reuse the existing approval engine for suggested customer replies and RepairShopr writebacks.
- Reuse the existing matching service when configured. If it is unavailable, collect minimum fields and mark the conversation review-ready without pretending a live match was performed.
- Update the Twilio webhook service from IP01.12 to call the intake processor after inbound persistence.

## State Model

```text
unknown
  -> identifying       when the sender has no strong customer identity yet
  -> matched           when a stored or newly found match is high confidence
  -> blocked           when spam checks fail

identifying
  -> collecting        when name or contact exists but service context is missing
  -> matched           when matching finds a high confidence RepairShopr record
  -> blocked           when spam checks fail

collecting
  -> review_ready      when minimum new-lead fields exist and no high confidence match exists
  -> matched           when a high confidence match exists
  -> blocked           when spam checks fail

matched
  -> review_ready      when enough service context exists for a staged update

review_ready
  -> blocked           only if later spam checks invalidate the conversation

blocked
  -> blocked           until a manager action in a later ticket
```

Minimum new-lead fields for review-ready:

- Sender phone or channel address.
- Customer name or business label.
- Problem description.
- Service address or clear location context.

## API Shape

Add a manager-only local debug read route if useful for tests and the manager dashboard:

### `apps/api/src/services/intake-spam-gate.ts`

Add deterministic spam evaluation:

- Block empty text with no media.
- Block messages containing more than three URLs.
- Block obvious high-risk phrases from a small local constant list.
- Raise score for repeated duplicate bodies in the same conversation.
- Do not block normal short repair requests.

Return a typed result with:

- `isBlocked`
- `score`
- optional `reason`

### `apps/api/src/services/customer-intake-state-machine-service.ts`

Add:

- `CustomerIntakeStore`
- `CustomerIntakeApprovalStore`
- `CustomerIntakeMatcher`
- `CustomerIntakeStateMachineServiceApi`
- `CustomerIntakeStateMachineService`

Behavior:

- Load the conversation and recent inbound messages.
- Run spam gate before any other action.
- Extract simple fields deterministically from the latest message:
  - sender phone already comes from the conversation.
  - name hints from phrases like `my name is`.
  - email with a conservative email regex.
  - address hints from numeric street-like text.
  - problem description from the message body when no narrower field is found.
  - preferred timing from scheduling phrases.
- Search RepairShopr only through the existing matching service when enough hints exist and the service is configured.
- High confidence match moves the state to `matched`.
- Medium-high or low confidence leaves state at `collecting` or `review_ready` and creates a manager-visible match review approval only if there is enough evidence.
- If no match exists and minimum new-lead fields are present, move to `review_ready` and stage a `repairshopr_writeback` approval with `risk = "customer_identity"` and `requiredRole = "manager"`.
- If missing fields remain, create or update a `customer_message` approval with a suggested prompt for only the next missing field.

## Implementation Boundaries

- Do not send SMS, WhatsApp, email, or other external messages.
- Do not write to RepairShopr.
- Do not fake live RepairShopr matching. Use fixture matchers in tests and leave production unmatched when live reads are unavailable.
- Do not introduce person names or legacy role wording in new code.
- Do not touch Linear, Notion, Slack, Gmail, Google Drive, or Tenex-owned systems.
