# IP01.8 - Approval Staged Change Engine - Implementation Plan

**Date:** 2026-05-22
**Story Points:** 8
**Project Plan:** PP01-service-referral-ops-agent
**Local Ticket:** RSJT-008
**Dependencies:** RSJT-003, RSJT-004

## Overview

Build the central staged approval queue for proposed customer messages, RepairShopr writebacks, appointment creation, manager overrides, and payout finalization. This ticket creates reviewable local state only. It must not send SMS or WhatsApp messages, write to RepairShopr, create appointments, or finalize payouts outside the local database.

The implementation should keep role vocabulary generic. Use `manager` and `tech` only, and do not introduce person names in code, route names, tests, fixtures, or database values.

## Proposed Structure

- Extend shared approval contracts with request, response, filter, and lifecycle schemas.
- Add a small DB migration so approvals track creator, required role, decision actor, original payload, current payload, source evidence, and risk.
- Add `ApprovalsRepository` for staged change persistence and audit events.
- Add `ApprovalService` for lifecycle rules and role enforcement.
- Add authenticated approval routes.
- Keep all external execution out of scope. Approving a staged change only moves local state to `approved`.

## API Shape

### `POST /approvals`

Creates a pending staged change.

```json
{
  "jobId": "00000000-0000-4000-8000-000000009001",
  "kind": "customer_message",
  "risk": "scheduling",
  "requiredRole": "manager",
  "payload": {
    "body": "We can schedule service tomorrow afternoon."
  },
  "evidence": [
    {
      "messageId": "00000000-0000-4000-8000-000000000201",
      "quote": "tomorrow afternoon"
    }
  ]
}
```

### `GET /approvals`

Returns staged approvals, filtered by optional query params:

- `state`
- `risk`
- `kind`
- `jobId`
- `requiredRole`

### `PATCH /approvals/:approvalId`

Edits a pending staged change payload while preserving the original proposal.

```json
{
  "payload": {
    "body": "We can schedule service tomorrow between 2 and 4."
  }
}
```

### `POST /approvals/:approvalId/approve`

Moves a pending approval to `approved` if the authenticated user has the required role.

### `POST /approvals/:approvalId/reject`

Moves a pending approval to `rejected`.

```json
{
  "reason": "Needs a different appointment window."
}
```

### `POST /approvals/:approvalId/expire`

Moves a pending approval to `expired`. Manager can expire any approval, and tech can expire approvals requiring `tech`.

## File-By-File Changes

### `packages/shared/src/domain/approvals.ts`

Extend the existing approval enums with:

- `ApprovalIdParamsSchema`
- `ApprovalFilterQuerySchema`
- `CreateApprovalRequestSchema`
- `EditApprovalRequestSchema`
- `RejectApprovalRequestSchema`
- `ApprovalRecordSchema`
- `ApprovalListResponseSchema`
- `ApprovalDecisionResponseSchema`

Use existing `ApprovalStateSchema`, `ApprovalKindSchema`, `ApprovalRiskSchema`, `SourceEvidenceSchema`, and `UserRoleSchema`. Payloads should be `z.record(z.unknown())` so later tickets can define narrower payload schemas per approval kind.

### `packages/db/src/schema.ts`

Update `approvals`:

- Add `createdByUserId`.
- Add `requiredRole`.
- Rename application field `approvedByUserId` to `decidedByUserId` and map it to the new DB column `decided_by_user_id`.
- Add `originalPayload`.
- Keep `payload` as the current editable payload.
- Add `updatedAt`.
- Add indexes for `requiredRole`, `risk`, and `kind`.

### `packages/db/src/migrations/0002_approval_staged_change_fields.sql`

Add the migration:

- Rename `approved_by_user_id` to `decided_by_user_id`.
- Add `created_by_user_id`, `required_role`, `original_payload`, and `updated_at`.
- Backfill `required_role` to `manager` for existing rows.
- Backfill `original_payload` from `payload`.
- Add foreign key for `created_by_user_id`.
- Add indexes for approval inbox filters.

### `apps/api/src/repositories/approvals-repository.ts`

Add repository methods:

- `create(input)`
- `list(filters)`
- `getById(id)`
- `editPending(id, payload)`
- `setState(id, state, actorUserId, metadata)`

Repository responsibilities:

- Store `originalPayload` and `payload` on create.
- Preserve `originalPayload` on edits.
- Write audit events for create, edit, approve, reject, and expire.
- Return typed shared `ApprovalRecord` objects.

### `apps/api/src/services/approval-service.ts`

Add service methods:

- `createApproval(user, input)`
- `listApprovals(filters)`
- `editApproval(user, approvalId, input)`
- `approveApproval(user, approvalId)`
- `rejectApproval(user, approvalId, input)`
- `expireApproval(user, approvalId)`

Rules:

- Only pending approvals can be edited, approved, rejected, or expired.
- A `manager` can approve, reject, or expire any approval.
- A `tech` can approve or expire only approvals whose `requiredRole` is `tech`.
- A `tech` can reject approvals whose `requiredRole` is `tech`.
- Approval does not execute external writes.
- Rejection does not execute external writes.
- Edited approvals preserve `originalPayload`.

### `apps/api/src/routes/approvals-routes.ts`

Add authenticated routes:

- `POST /approvals`
- `GET /approvals`
- `PATCH /approvals/:approvalId`
- `POST /approvals/:approvalId/approve`
- `POST /approvals/:approvalId/reject`
- `POST /approvals/:approvalId/expire`

Use shared schemas for params, query, and bodies. Return `404` for missing approvals, `409` for approvals that are no longer pending, and `403` for insufficient role.

### `apps/api/src/app.ts`

Wire the default approval service when `db` is decorated and allow tests to inject an approval service.

### Tests

Add tests for:

- Shared schema parsing for create and filter requests.
- Repository create, edit, list filters, and audit events.
- Service role enforcement for manager-only approvals.
- Service no-op execution behavior on approve and reject.
- Route authentication, validation, filtering, edit, approve, reject, expire, 403, 404, and 409 cases.
